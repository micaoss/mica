# s905x5m: BM201 / Amlogic S905X5M (S7D)

`s905x5m` is a **hardware board**. It has been a release target since
2026-09-19, so its images are published like every other board's — and **there
is no supported way to install Mica OS onto a blank board**, for the reason
under Flashing below.

Snapshot written 2026-09-20, from the dossier
[`docs/boards/s905x5m.md`](../boards/s905x5m.md) and
`mica-build:boards/s905x5m/`; status is owned by the
[tiers table](../boards/support-tiers.md#current-boards).

## At a glance

| | |
|---|---|
| Hardware | X88 Pro X5M / BM201 development units |
| SoC | Amlogic S905X5M (S7D) |
| Architecture | `arm64` |
| Boot chain | Mica OS Amlogic firmware in eMMC boot0 → the SD system disk (`mmc 0`) → **required signed FIT**, its public key embedded in the exported BL33 control DTB → signed kernel and authenticated native init → SYSTEM → signed verity root/support → systemd |
| Firmware form | `amlogic-boot0` — U-Boot lives in eMMC boot0, **not in the image** |
| Partitions | FIRMWARE / SYSTEM / DATA, on SD |
| Kernel | `hardkernel/linux` (`9ea2aa83`) with fourteen local patches, the board DT and the Seekwave sources |
| U-Boot | `CoreELEC/u-boot` (`5f7ac2b1`), patches 0001–0007 and 0019–0020 |
| Release target | yes, by user decision on 2026-09-19; first release `s905x5m.20260920-0033` |
| Tier | bring-up |
| Boot assurance | I1; no hardware-rooted claim |

Automatic boot arms the 60-second Meson watchdog, which runs in userspace-feed
mode with NOWAYOUT applied before device registration. The boot path imports no
U-Boot environment and no boot script.

## Partition layout (on SD)

| Partition | Range | Note |
|---|---|---|
| `FIRMWARE` | sector 64 to 128 MiB | **carries no SD boot loader**: two 64 KiB boot records at absolute 120 and 124 MiB, and padding |
| `SYSTEM` | 128–1152 MiB | ext4 + verity |
| `DATA` | from 1152 MiB, 256 MiB at the factory | the only partition that grows |

The eMMC boot0 firmware is described by a signed external receipt: the payload
sits after a 512-byte vendor-generated header and is bounded to 4,193,792
bytes. Native read-back finds the eMMC hardware boot partition independently of
the SD system disk. Ordinary root and kernel updates **do not write firmware**.

## Console

Serial `ttyS0` at **921600 baud**, with `earlycon=aml_uart,0xfe07a000`.
**Confirm the connector and voltage against the specific board's hardware
record before wiring.**

## Obtaining an image

The products are `s905x5m-dev` and `s905x5m-prod`, published since
`s905x5m.20260920-0033`. **Published is not installable**: see below.

## Flashing

**There is no supported installation path today.**

The reason is where the firmware lives. Mica OS's U-Boot
(`u-boot.bin.signed`) executes from the eMMC boot0 region behind a 512-byte
Amlogic header generated on the target, and the loader refuses to boot
automatically when the source is not boot0. The published disk image covers SD
media only — FIRMWARE, SYSTEM and DATA from sector 64 — so **writing it to a
card installs no boot loader**. Only a board whose boot0 already carries the
matching Mica OS U-Boot can start from that card.

What exists towards a future procedure:

- `make -C boards/s905x5m uboot` builds the signed U-Boot and its DDR firmware.
- `make -C boards/s905x5m uboot-package` builds an Amlogic v2 `update.img`
  (a pinned `aml_image_v2_packer`, checked by unpacking it again) carrying the
  signed U-Boot as `bootloader.PARTITION` and **deliberately omitting**
  `gpt.bin` and `bootloader_a`, so the burn frames the hardware boot region
  only and cannot touch the user-area GPT.

What is missing: which host tool consumes that image, how boot0 is written and
read back, and how a bricked board is recovered. None of it is written down or
tested; it is bench work owned jointly by `mica-boards` and `mica-build`. See
[flashing](../user/flashing.md) section 6.

> status: unsupported

## First boot

As on the other FIT board: a one-second native console countdown that consumes
no trial, then the watchdog is armed, a bounded native record is selected,
the attempt is persisted and read back, and the FIT is verified. DATA grows on
first boot. None of this has run on hardware.

## Updates

`full`, `root` and `kernel` archives are published. An ordinary update never
touches the firmware in eMMC boot0 — firmware maintenance is a separate signed
write-and-read-back workflow, and the generic Mica OS firmware maintenance
**deliberately refuses** this hardware boot target. See
[update packages](../user/update-packages.md).

**Nothing in this tree starts this board's images** (no suite boots a FIT
image), so the update path has no end-to-end record here.

## Recovery

- Available on a device that boots: read-only diagnosis, manual rollback,
  configuration reset, application-data reset.
- **Unavailable**: credential recovery and full-factory reset, for want of a
  declared physical recovery action.
- **The floor** is Amlogic USB burning mode, entered through the board's
  `aml_sdc_burn` flow and its `update.img` container. It is open to anyone with
  physical access, and it is also this board's recorded physical-access
  boundary. Actual installation and recovery still need bench qualification.
- There is no secure erase.

See [recovery](../user/recovery.md).

## Known limitations

- SD boot requires the matching Mica OS firmware in eMMC boot0; original vendor
  firmware does not implement this signed-file policy.
- No compatibility reader, no historical-layout installer and no migration of
  existing state.
- Opaque Amlogic stages and radio firmware keep their recorded auditability and
  distribution-licence limits.
- Native crun cannot be executed under the current CI executor, which cannot
  run its memory-file re-exec.
- No physical row is recorded, and `RFCT-922` — Bluetooth pairing and a profile
  against a controlled peer — is still open.
