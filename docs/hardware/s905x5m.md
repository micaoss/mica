# s905x5m: BM201 / Amlogic S905X5M (S7D)

`s905x5m` is a **hardware board**. Its images are built and verified like every
other board's, and **no step of installing or booting one has been recorded on
a unit**: every physical statement on this page is unverified.

The board has two storage layouts. `s905x5m.basic` and `s905x5m.emmc-full` put
the system on the eMMC and are installed whole, loader included, as a USB
burning package. `s905x5m.sd-full` puts the system on an SD card and needs the
matching Mica OS U-Boot in the board's eMMC boot0, which its release carries
as a second package.

Status is owned by the [status table](README.md#current-boards).

## At a glance

| | |
|---|---|
| Hardware | X88 Pro X5M / BM201 development units |
| SoC | Amlogic S905X5M (S7D) |
| Architecture | `arm64` |
| Boot chain | Mica OS Amlogic firmware in eMMC boot0 → **required signed FIT**, its public key embedded in the loader's control DTB → signed kernel and authenticated native init → SYSTEM → signed verity root/support → systemd |
| Firmware form | U-Boot lives in eMMC boot0, **never in the disk image** |
| Partitions | FIRMWARE / SYSTEM / DATA, on SD or on the eMMC user area |
| Kernel and U-Boot | vendor trees, pinned with their patches in `mica-build:boards/s905x5m/bsp.env` |
| Tier | bring-up |
| Boot assurance | I1; no hardware-rooted claim |

Opaque Amlogic stages sit in front of U-Boot. Automatic boot arms the
60-second Meson watchdog before it consumes an attempt, and imports no U-Boot
environment and no boot script.

## Partition layout

On SD (`sd-full`):

| Partition | Range | Note |
|---|---|---|
| `FIRMWARE` | sector 64 to 128 MiB | **carries no boot loader**: two 64 KiB boot records at 120 and 124 MiB, and padding |
| `SYSTEM` | 128–1152 MiB | ext4 + verity |
| `DATA` | from 1152 MiB, 256 MiB at the factory | the only partition that grows |

On eMMC (`basic`, `emmc-full`), beside the vendor's own partitions, which are preserved:

| Partition | Range | Note |
|---|---|---|
| `firmware` | 128–136 MiB | the two boot records |
| `system` | 136–1160 MiB | ext4 + verity |
| `data` | from 1160 MiB, 256 MiB at the factory | the only partition that grows |

The authoritative geometry is `mica-build:boards/s905x5m/layout.tsv` and
`mica-build:boards/s905x5m/layout-emmc.tsv`. An ordinary update never writes
the firmware in boot0.

## Console

Serial `ttyS0` at **921600 baud**, with `earlycon=aml_uart,0xfe07a000`.
**Confirm the connector and voltage against the specific board's hardware
record before wiring.**

The products, each released as `s905x5m.<variant>.<YYYYMMDD-HHMM>`:

| Product | Storage | Containers | Its release carries |
|---|---|---|---|
| `s905x5m.basic` (the default) | eMMC | no | the USB burning package, `.burn.img.gz` |
| `s905x5m.emmc-full` | eMMC | yes | the USB burning package, `.burn.img.gz` |

[download](../start/download.md).

## Flashing

**Onto eMMC (`basic`, `emmc-full`), unverified.** The USB burning package is an Amlogic
v2 burning image for the vendor USB Burning Tool. It writes the partition
table, both bootloader targets, the vendor device tree and the three Mica OS
partitions, and leaves the vendor's other partitions alone. Holding the
recovery key at power-on puts the board into USB burning mode. The build
unpacks every package it makes and proves each payload is its source; nobody
has burned one onto a unit.

**Onto SD (`sd-full`), unverified.** Write the decompressed disk image to the
whole card. **Writing it installs no boot loader**: the image covers
FIRMWARE, SYSTEM and DATA only, and the board starts from it only when its
eMMC boot0 already carries the matching Mica OS U-Boot. That is the boot
loader package beside the image in the same release, a USB burning package
installed over the same USB burning mode
(`mica-build:boards/s905x5m/loader/README.md`).

Detail is in [flashing](../start/flashing.md) section 6.

> status: unsupported

## First boot

A one-second console countdown that consumes no attempt, then the watchdog is
armed, a boot record is selected, the attempt is persisted and read back, and
the FIT is verified. DATA grows on first boot. None of this has run on
hardware.

## Updates

`full`, `root` and `kernel` archives are published, and `core` for a core
release. An ordinary update never touches the firmware in eMMC boot0, and the
generic firmware maintenance deliberately refuses this board's boot target.
See [updates and rollback](../operate/updates.md).

Nothing in these repositories starts this board's images, so the update path
has no end-to-end record here.

## Recovery

- Available on a device that boots: read-only diagnosis, manual rollback,
  configuration reset, application-data reset.
- **Unavailable**: credential recovery and full-factory reset, for want of a
  declared physical recovery action.
- **The floor** is Amlogic USB burning mode, entered with the recovery key at
  power-on. It is open to anyone with physical access, and it is this board's
  recorded physical-access boundary. It costs every partition and the device
  identity.
- There is no secure erase.

See [recovery](../operate/recovery.md).

## Known limitations

- SD boot requires the matching Mica OS firmware in eMMC boot0; the original
  vendor firmware does not implement the signed-file policy.
- Opaque Amlogic stages and radio firmware keep their auditability and
  distribution-licence limits.
- The loader does not rebuild byte-identically, because the vendor signing
  step is not deterministic.
- No physical row is recorded, and Bluetooth pairing against a controlled peer
  is untested.
