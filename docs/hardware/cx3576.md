# cx3576: CX3576-Z / Rockchip RK3576

`cx3576` is a **hardware board**, named for the product, and the in-tree
porting reference. Its images are published and its flashing path is
implemented, and **nothing in these repositories starts its images** — no suite
boots a FIT image.

A `cx3576` hardware boot was reported by the user on 2026-09-20, the first
physical boot report this project has had. It is **a report and nothing more**:
a pass row carries a date and an evidence reference, this arrived without an
artefact, so no row in the tiers table moves and the dossier's physical rows
stay `not tested`. Turning it into a row is `mica-boards`'s to do.

Snapshot written 2026-09-20, from the dossier
[`docs/boards/cx3576.md`](../boards/cx3576.md), the BSP sync record
[`cx3576-bsp-sync.md`](../boards/cx3576-bsp-sync.md) and

## At a glance

| | |
|---|---|
| SoC | Rockchip RK3576 |
| Architecture | `arm64` |
| Boot chain | BootROM → vendor DDR/SPL/TF-A → pinned Mica OS U-Boot → **required signed FIT configuration** → kernel and authenticated native init → SYSTEM → signed verity root/support → systemd |

| Partitions | FIRMWARE / SYSTEM / DATA |

| Tier | bring-up |

There are vendor blobs in the boot chain: DDR init `v1.12` and TF-A
`bl31 v1.24` from Rockchip `rkbin`. Software FIT enforcement does **not** prove
that those first mutable stages are authenticated by hardware.

## Hardware and feature state

`BOARD_FEATURES="wifi bluetooth display status-led can usb-gadget containers"`.
"Declared" means the board declares the feature and ships the packages and
initialisation for it; every physical row is untested.

|---|---|---|

| Bluetooth | declared, untested on hardware | the same module as Wi-Fi |

| Boot logo | implemented | the Mica OS icon above its wordmark, rendered at build time |
| CAN | declared, untested on hardware | one of the `hwinit` concerns |
| USB OTG / USB gadget | declared, untested on hardware | the gadget getty udev rule ships with the board package |
| Status LED | declared, untested on hardware | — |
| RTC | **presence unconfirmed** | the device tree declares an `AT8563`/`hym8563` at `0x51` on `i2c7`, `board.env` records no RTC fact, and neither driver nor backup cell has run on a unit. ## Partition layout

| Partition | Range | Note |
|---|---|---|
| `FIRMWARE` | sectors 64–36863 (below 18 MiB) | holds U-Boot (sector 64; the magic `RKNS` sits at byte offset 32768) and two 64 KiB CRC-protected boot records at 16 MiB and 17 MiB |
| `SYSTEM` | from 18 MiB, 1024 MiB | ext4 + verity, immutable component files and two signed deployments |
| `DATA` | from 1042 MiB, 256 MiB at the factory | grown to the medium on first boot |

The complete factory image is 1299 MiB = 1,362,100,224 bytes including the GPT
tail. The GPT covers the loader and both records, so DATA growth cannot discard
them.

## Console

Serial `ttyFIQ0` at **1500000 baud**, with
`earlycon=uart8250,mmio32,0x2ad40000`; `net.ifnames=0`.

## Flashing

**The image carries its own boot loader**: U-Boot sits at sector 64 inside the
protected range, so writing the image writes the loader too — there is no
separate idblock step, and this board produces no vendor `update.img`.

Flashing is an operator procedure over USB with `rkdeveloptool`; the build
tree carries no flashing tooling (user decision, 2026-09-22). The image must
be the decompressed `.img`, exactly 1,362,100,224 bytes.

Device in **Loader/RockUSB** mode (U-Boot runs and its gadget enumerates):

```sh
rkdeveloptool wl 0 mica-cx3576-<stamp>.img          # write the whole disk
rkdeveloptool rl 0 36864 boot.bin                     # read the loader and record region back...
cmp boot.bin <(head -c $((36864*512)) mica-cx3576-<stamp>.img)
rkdeveloptool rl 36864 2623488 rest.bin               # ...then everything after it
cmp rest.bin <(tail -c +$((36864*512+1)) mica-cx3576-<stamp>.img)
rkdeveloptool rd                                      # reset, only after both comparisons passed
```

Device in **Maskrom** mode (the loader region is absent or broken): push the
committed vendor loader first, then the Loader sequence above.

```sh
sha256sum -c boards/cx3576/loader/MiniLoaderAll.bin.sha256   # in the mica-build tree
rkdeveloptool db boards/cx3576/loader/MiniLoaderAll.bin
```

- The loader region (the first 36,864 sectors) is read back first and on
  its own, because a partial or corrupt write there is the one failure that
  bricks the board past the recovery key. Do not run `rd` after a mismatch:
  the device stays in Loader mode and can be flashed again.
- **Do not cut power, unplug or reset the board between `db` and `rd`.**
- Prerequisites: `rkdeveloptool` on `PATH` and USB access to the device
  (the tree ships no udev rules). On macOS build it natively as
  [`docs/boards/cx3576/rkdeveloptool/README.md`](../boards/cx3576/rkdeveloptool/README.md)
  describes.

Unverified: every step against real hardware, the key or pad sequence that
enters Maskrom, and any SD-card boot fallback. Detail is in
[flashing](../user/flashing.md) section 5.

> status: board-dependent — evidence: `mica-build:boards/cx3576/loader/MiniLoaderAll.bin.sha256`, `docs/boards/cx3576/rkdeveloptool/README.md`, `docs/user/flashing.md`

## First boot

DATA growth, two factory deployments and the health gate work as on the UEFI
boards; the difference is that the boot records live in redundant U-Boot
environments inside the firmware range (`tries = 3`) instead of in loader
entries on an ESP.

U-Boot starts the watchdog before it touches eMMC, validates the current GPT
geometry, selects a record, writes, flushes and reads back the decremented
attempt, and only then loads its FIT; **failing to persist refuses the
launch**. Both records exhausted or invalid enters local rockusb recovery.

## Updates

`full`, `root` and `kernel` archives, as on every board. A/B is two file-based
deployments on SYSTEM rather than a partition pair, so there is no "other slot"
to flash. See [update packages](../user/update-packages.md) and
[update and rollback](../user/update-rollback.md).

**Note**: nothing in this tree starts this board's images, so the chain from
write through first boot, update, confirmation and rollback has no end-to-end
run that left evidence.

## Recovery

The ladder is the one every board follows; the bottom two steps differ:

- Available: read-only diagnosis, manual rollback, configuration reset,
  application-data reset, whole-disk reflash.
- **Unavailable**: credential recovery and full-factory reset —
  `BOARD_RECOVERY_ACTIONS=""`, so no presence assertion can be produced.
- **The floor** is rockusb: the recovery button at power-on, the automatic
  entry when boot fails, or Maskrom when the loader region itself is gone,
  followed by a whole-disk reflash from Maskrom. It costs every partition
  **and the device identity**.
- There is no secure erase; no erase primitive on this eMMC has been verified.

See [recovery](../user/recovery.md).

## Known limitations

- Physical boot, eMMC power cuts, watchdog handoff and reset cause, the full
  USB flash, RTC and peripheral qualification all need a named local bench
  device.
- DDR init and TF-A are vendor blobs; software FIT enforcement proves neither
  hardware authentication of the first mutable stages nor a closed debug path.
- The accepted radio package targets AIC8800D80; the AP6275S SKU is not
  qualified.
- The exact eMMC part and board revision still need physical evidence.
- Standalone sha256 digests of the `rkbin` blobs and the vendor MiniLoader are
  **not on file**, which the intake rubric requires for binary inputs; it is
  recorded as a known limitation.
- Development boot, content and metadata keys are separate test inputs: no
  OTP/fuse change and no production key ceremony is claimed.
- U-Boot keeps an interactive console (`BOOTDELAY=1`, with `fdt`, `md`/`mw`
  and `go`), so someone at the serial port can alter the in-memory control DTB
  or run an unsigned binary.
