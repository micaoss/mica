# 安全生命周期

谁持有哪些信任材料、它们如何生成、轮换和恢复，以及发布和漏洞如何处理。各密钥驱动的机制见
[签名](signing.md)；它们防御什么见[模型](model.md)。

## 1. 项目的现状

- **迄今为止的每个发布都用开发密钥签名。**生产密钥的保管尚未建立，也没有任何发布声称如此。设备会报告它
  信任的是生产密钥还是开发密钥（`GET /api/v1/system/info`）。
- 没有公开的安全联系方式、没有公告渠道、没有支持期，也没有终止支持政策。
- 没有机队证书颁发机构，也没有设备登记。

下文把已经存在的东西与待建立的流程分开说明。

> status: unsupported

## 2. 信任材料

| 材料 | 认证对象 | 生成方式 | 轮换 | 丢失或泄露时 |
|---|---|---|---|---|
| **启动密钥** | 板卡启动的加载器和内核：UEFI 下的 UKI，U-Boot 下的 FIT | 构建输入，与其他密钥分开 | 携带新锚点的新加载器或固件；固件只能经离线维护途径更换 | 整盘重刷 |
| **内容密钥** | 根、support 和 core 组件镜像，通过内核对每个 verity 映射要求的签名 | 构建输入；公开证书内置在内核中 | 一个在旧证书旁边或代替旧证书携带新证书的内核；从不是可变密钥环 | 没有可接受的组合时整盘重刷 |
| **元数据密钥** | 部署描述符和固件记录 | 构建输入；公钥在签名的内核中 | 重叠集合：先加入新密钥再移除旧密钥，只要还有已发布制品依赖某个密钥就不移除它 | 没有可接受的组合时整盘重刷 |
| **API 的 TLS 身份** | 对已经接受过它的浏览器而言"还是上次那台设备" | 第一次提供 HTTPS 时在设备上自签名生成 | 由管理员替换，上传证书链或生成新的自签名证书 | 重新生成；配置重置会删除它 |
| **管理员密码和 API 令牌** | 管理 API | 由认领设备的人设置 | 通过 API | 无：见下文 |
| **SSH 授权密钥** | root shell | 由管理员登记 | 编辑列表 | 无：见下文 |
| **临时 root 密码** | 下次启动前的 SSH 和本地控制台 | 由管理员设置 | — | 按设计在下次启动时消失 |
| **owner 证书** | 仅驱动扩展，在带 owner 密钥环的内核上 | 由管理员登记；每次变更记录在 SYSTEM 上 | 添加或删除；变更在下次启动时生效 | 删除它；出厂重置会删除全部 |

贯穿整张表的规则：

- **三个签名域使用不同的密钥。**一个域的密钥不能顶替另一个。
- **私钥从不进入镜像、软件包或发布。**构建使用公开证书；签名在持有私钥的地方进行。
- **信任锚点不是设置。**没有任何 API、配置文档或更新来源能添加或替换锚点；它们只随携带它们的签名内核
  变化。owner 证书不是系统的锚点：它们在系统镜像映射之后才加载，只认证驱动扩展。
- **已安装的部署可离线启动。**启动不等待网络、吊销列表或时钟。没有过期时间，所以在服务器上扣下或撤下
  一个发布并不会吊销设备已在运行的东西。
- **代数只升不降**，失败的部署会被记住，所以设备不会回到它拒绝过的发布。
- **丢失管理员凭据没有软件恢复手段。**丢失管理员密码、全部令牌和全部密钥的运维者只能重刷设备，代价是
  设备上的一切（[访问](../../reference/access.md) 第 7 节）。支持人员会事先说明这一点。
- 首次启动时生成的设备密码不认证任何东西，也从不作为凭据提供给客户
  （[配置](../../integrate/provisioning.md) 第 2 节）。

> status: shipped — evidence: `docs/security/signing.md`, `mica-core:docs/mica-core.md`, `mica-build:README.md`

## 3. 保管

保管按角色划分，每个流程恰好有一个负责的角色。

| 角色 | 负责 |
|---|---|
| 发布负责人 | 密钥保管与仪式、发布、支持期 |
| 安全负责人 | 漏洞接收、严重程度、公告、事件响应 |
| 生产负责人 | 工厂输入、记录、隔离和返工（[量产](../../reference/manufacturing.md)） |
| 支持负责人 | 现场升级处理、退货、把故障关联到发布和工厂记录 |

在人手允许时，发布负责人和安全负责人由不同的人担任：发布路径被攻破，正是安全负责人必须能够独立应对的
事件。

生产私有材料只存在于仪式介质和发布主机上。CI 使用一次性的开发材料，从不导入生产密钥。构建会拒绝出厂
shadow 文件中带有可用密码的镜像，开发密钥标记随公开默认值一起传递，所以发布闸门和设备都能报告它。

> status: proposed — evidence: `docs/security/signing.md`

## 4. 发布

一个发布是一个产品，经签名，由 `mica-build` 发布（[发布如何进行](../releases/how-releases-work.md)）。用开发
材料签名的发布是开发发布；候选或稳定发布要等待生产密钥。通道之间的晋升、浸泡要求、支持期和终止支持通知
是待定义的流程，目前没有相应的工具或承诺。

确实存在一道闸门：声明超出其板卡已记录证据的发布（包括高于板卡的保证等级），在组装其清单时会被拒绝。

> status: shipped — evidence: `mica-build:src/image/release-manifest.ts`, `mica-build:src/boot/dev-keys.ts`

## 5. 安全响应

这些目前都还没有运作的渠道；是待建立的流程。

- **接收。**公开的联系方式和披露政策。在它存在之前，请私下报告给维护者。每份报告都会得到确认、记录和
  严重程度。
- **严重程度**，对照已声明的[模型](model.md)及其限制来判断，所以重述已记录限制的报告会以文档作答：

  | 严重程度 | 含义 | 修复目标 |
  |---|---|---|
  | critical | 无凭据攻破管理平面；接受了签名本应拒绝的更新；代码在经校验的根之外存活 | 紧急发布 |
  | high | 超出已记录的 root 等价范围的提权；绕过凭据机制；阻断更新或恢复 | 下一个发布 |
  | medium | 需要本地访问或特殊配置的弱点；不到凭据级别的信息泄露 | 计划内的发布 |
  | low | 加固上的缺口 | 随相关工作一起 |

- **公告**，每个已修复漏洞一份，写明受影响的发布和板卡、修复的发布以及任何临时规避方法。公告也是撤回
  夸大声明的方式。
- **事件**：遏制（暂停发布）、评估（哪些密钥、发布和设备）、轮换（第 2 节对应的那一行）、通知（包括无法
  远程修复的部分：重新锚定设备需要物理接触）、记录。

> status: proposed — evidence: `docs/security/model.md`
