# 签名组件的信任与轮换

当前的契约认证三个相互独立的面。经认证的引导加载器接受 UKI/FIT；该内核携带内容锚点和元数据锚点；早期
init（`mica-runkit`，位于签名的 initramfs 中）认证部署元数据并打开签名的根/support 映射。不读取任何更早的
更新格式或可变的命令行信任输入。

## 制品与签名归属

| 制品 | 签名绑定的内容 | 使用者 |
|---|---|---|
| UKI/FIT | 内核、initramfs、固定策略，以及适用时的 DTB | UEFI，或要求签名的 U-Boot 控制 FDT |
| 根/support 镜像 | 对根哈希的 PKCS#7 签名；签名元数据绑定完整的几何参数、哈希、长度和签名字节 | 内核 dm-verity 和原生元数据校验器 |
| 部署 | 签名的部署描述符：产品/板卡/架构/代数/版本，以及完整的内核/根身份；签名的 `product` 字段（例如 `uefi-x64.basic`）是必填的，其他产品的设备会拒绝它 | 出厂组装器、早期 init 和安装器 |
| core 组件 | 每个软件包一个（`micad`、`mica-apid-ui`）：用内容密钥签名的 verity 镜像、其根接口级别及其需求 | 早期 init，把它叠加在根上 |
| 目录 | **未签名**：更新根下的清单和每个发布的文档；信任来自每个发布签名的描述符 | 获取客户端 |
| 固件 | 板卡/架构/代数/制品和固定的写入目标 | 独立的固件发布者、离线维护者和原生回读 |
| 驱动扩展 | 对镜像根哈希的 PKCS#7 签名（以及签名的模块），签名密钥链到内核的内置密钥环或已登记的 owner 证书；不是 Ed25519 | 内核，在早期 init 封存 owner 密钥环之后映射它时 |

这些文档的模式名称和版本见 `mica-core:docs/mica-core.md` 6.2 节。

**对已部署的读取方而言，这些载荷不接受新增字段，由此得出的顺序与"生产者先行"的直觉正好相反。**
`mica-core:crates/mica-deploy/src/components.rs` 中**每个被反序列化的结构**都带有
`#[serde(deny_unknown_fields)]`。该文件中的其他结构（`ContractError`、`RootFacts`、`DeploymentPaths`）不派生
`Deserialize`，从不从载荷中解析，所以**这条约束没有例外，也没有可以添加字段的宽松结构**：添加字段不会平滑
降级，**运行今天的 `mica-deploy` 的设备会拒绝整条记录。**因此新字段只能按这个顺序传递：

1. 读取方在 `mica-core` 中修改并接受该字段；
2. 修改进入一个 `mica-core` 发布；
3. **该发布到达设备**；
4. 只有在此之后，`mica-build` 才可以输出该字段。

**凡是从"格式归生产者所有"出发推理的人都会把这个顺序弄反**，而弄反就意味着发布已部署设备会拒绝的记录。

`mica/rootfs/v1` 不带 `version` 字段，所以根没有任何变化的发布保留其 rootfs 身份；发布的身份只在签名部署的
`version`、`generation` 和 `product` 中。部署和目录分别是 `mica/deployment/v1` 和 `mica/catalog/v1`
（`mica-core:docs/mica-core.md` 6.2 节）。

Ed25519 封套格式由 Rust 和 Bun 共用：其键的顺序为 `schema`、`keyId`、`payload`、`signature`，`keyId` 是
Ed25519 公钥的十六进制 SHA-256。解析会拒绝未知字段、有歧义/非规范的内容、不匹配的组件 ID、意外的路径和无效
的边界。离线归档（扩展名 `.micaupd`）以 8 字节魔数 `MICAUPD1` 开头，接着是描述符长度（u32，大端）、签名的
描述符、对象数，以及每个对象的摘要、大小和字节；它们复用部署签名，只携带按摘要/长度寻址的有界对象。对象数
可以是 0 到描述符对象数之间的任意值：归档省略的每个对象都必须已在存储中，归档不会因为对象数与描述符不同
而被拒绝。因此一个签名部署会以使用同一描述符的 `full`、`root` 和 `kernel` 三种归档发布。

元数据信任存在于经认证的内核策略中。公开的出厂更新设置选择来源和策略；它们不能替换锚点。已安装的系统
启动不依赖于能否连上更新服务器。更新文档未签名，也没有过期时间；获取新发布时会检查清单修订号是否单调
递增。

## 内容校验

内核要求根和 support 映射都有签名的根哈希。support 镜像拥有恰好对应其内核版本的模块、固件，以及需要时的
无线监管数据库。根拥有用户空间和空的 support 挂载点。早期加载器在绑定 support 并启动 systemd 之前校验所选
描述符的关联。

签名校验认证 verity 根，之后的读取逐块校验。启动时不会预读镜像的每个块。安装和离线校验还会对照签名的
长度/摘要声明对完整制品做哈希。潜在的损坏在读到受影响的块时被发现；不声明启动期间检查过未读取的块。

经度量的内核集成会接受超出 X.509 有效期的已编译内容证书，并拒绝 root 吊销内置锚点的尝试。因此时间过期和
运行时吊销都不是撤回手段。要移除一个内容密钥，需替换接受它的内核。

## 轮换

1. 在相关的接受方制品中引入启动/内容/元数据密钥的重叠。
2. 校验预期的新旧签名，包括一条保留的可启动记录。
3. 发布新组件，观察启动和健康确认。
4. 在后续的接受方制品中移除旧锚点，并在回退可用的情况下验证其签名被拒绝。

发布是静态的：目录未签名，没有服务器检查密钥的使用。在一个元数据密钥离开接受它的内核之前，仍在其下提供的
每个发布都要重新签名或撤回。

固件发布独立于正常的系统目录。离线 EFI 维护把经认证的旧加载器保存在 ESP 之外，写入并同步替换品，然后
校验回读。RockUSB 维护保存并比对整个保留分区，只写固定的加载器范围，从不重置设备。系统根或内核的安装都
不会写加载器字节或登记平台密钥。

## 证据的限度

真实的 QEMU Secure Boot 证明了 UKI 的强制执行、EFI 加载器的替换、恢复和密钥移除。生产 U-Boot 控制 FDT 的
提取和 FIT 签名测试证明了其配置的签名者策略。原生回读和 IO 故障测试覆盖软件事务。板卡页面记录各板卡的
结果（[支持层级](../hardware/README.md#当前板卡)）。cx3576 物理 ROM/SPL 信任、看门狗交接、USB 维护和存储
断电持久性仍是独立的台架验收闸门。开发密钥明确只是开发级别。
