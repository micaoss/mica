# 设计：安全模型——威胁与物理接触边界

> Mica OS 防御什么、针对谁、按边界分别说明——运行时根文件系统完整性、更新真实性、启动链真实性、数据
> 机密性、恢复/配置以及以 root 运行的应用分开陈述，因为这六者的机制不同、成熟度不同、能诚实声明的内容
> 也不同。配套文档：`docs/security/signing.md`（密钥流程）、`docs/reference/ro-root.md`（verity 根）、
> `docs/reference/access.md`（调试访问）和 `docs/security/lifecycle.md`（谁在何时运行什么）。

## 0. 如何阅读状态标记

只以文字存在的安全控制，没有任何机制会发现它缺失，所以下面每个机制都带有以下之一：

- **[implemented]**——代码存在并按路径点名。
- **[partial]**——部分存在；缺失的部分会点名。
- **[proposed]**——没有任何代码，只有文字。

## 1. 物理接触边界

当前的验收使用开发镜像和明确的测试密钥。不声明硬件信任根启动、已熔丝的密钥状态或封闭的调试策略。能
接触存储的人可以读取或破坏未加密的 DATA，并使用现有的重刷/恢复通道。只要执行检查的启动阶段和已登记的
锚点仍可信，UEFI/FIT 签名仍会拒绝未授权的启动对象；这些软件检查并不认证未经验证的第一个可变阶段。

离线配置凭对其介质的物理持有而获得授权，并受已认领设备策略的约束。它与签名的系统更新是两回事。每块
物理板卡都必须明确记录其恢复和调试暴露面。

## 2. 边界 (a)：运行时内容完整性——**[implemented]**

经认证的原生 init 校验所选的部署、板卡/内核关联和几何参数。内核在为根和 support 建立只读 dm-verity 映射
之前，要求分离的根哈希签名由内置的内容锚点签发。块按需校验；损坏但尚未读取的块在访问时被发现。启动时
不强制做完整镜像哈希扫描。

support 拥有匹配的模块和板卡固件，在 udev 之前挂载。根拥有用户空间和不可变的 `/var` 骨架。选定的持久
叶子目录绑定 DATA 命名空间；易失路径有明确的内存或可丢弃配额。不使用未经校验的可写模块目录或整棵可写的
`/var`。

驱动扩展以同样的方式映射，在早期 init 封存 owner 密钥环之后：其根哈希签名链到内核的内置密钥环或某张
owner 证书，而根、support 镜像和 core 组件在加载任何 owner 证书之前就已映射（[安全概览](overview.md)）。

这保护的是在经认证的运行中内核之下的已校验内容。它不加密 DATA，也不约束有意获得特权的管理员。见
[只读根](../reference/ro-root.md)和[可写存储](../reference/storage.md)。

## 3. 边界 (b)：更新真实性——**[implemented]**

三个独立的签名域分别认证启动可执行文件、不可变内容和发布元数据。原生安装在持久发布之前校验严格的签名
部署以及对象的精确长度/摘要。目录中没有任何东西会过期；代数下限和失败 ID 阻止被拒绝或更旧的发布回来。
已安装的有效部署在离线和没有网络时间的情况下仍可启动。

安装、确认、垃圾回收和重置共用一把 DATA 事务锁。current、fallback 和已暂存的引用保护各自的不可变对象；
失败或不完整的发布不会暴露不完整的候选。已暂存的发布不改变持久模式。回滚切换组件引用，不会恢复 DATA
上的写入。不声明硬件单调计数器和物理介质重放保护。

创建开发密钥是显式的操作，并要求一个新的输出目录。私有输入在镜像之外；元数据锚点来自经认证的内核策略，
而不是可编辑的用户空间默认值。系统信息中的标记报告的是开发来源，而不是经度量的固件执行。见
[发布签名](signing.md)和[更新](../reference/updates.md)。

## 4. 边界 (c)：启动链真实性——按板卡的证据

在 uefi-x64 和 uefi-arm64 上，签名的 systemd-boot 管理器选择带计数的条目，固件在已登记的 Secure Boot 锚点
下认证 UKI。无法持久化一次尝试时拒绝启动。在 cx3576 上，固定的 C 固件策略要求签名的 FIT 配置，禁用持久的
命令导入，在访问 eMMC 之前启动看门狗，并在加载 FIT 之前刷新并回读尝试计数的更新。qemu-armhf 的加载器只
检查 FIT 的哈希（`bootTrust` 为 `none`：QEMU 把控制设备树交给 U-Boot，因此无法在其中嵌入密钥）；设备报告
启动未经校验、没有验证启动，而其内容仍有 verity 签名，元数据仍经过认证。

只有健康闸门能确认部署。三次失败的试运行用尽后不会重新填充。不可用的共享存储和耗尽的部署会进入明确的
恢复结果。内核 panic 使用重启策略；挂起需要独立证明的看门狗覆盖。QEMU 和沙箱的结果不能证明物理 eMMC 的
断电行为，也不能证明板卡从固件到健康闸门的完整看门狗交接。

启动密钥、内容密钥和元数据密钥的重叠/移除是彼此独立的操作。固件维护是经认证的离线流程，带恢复制品和
回读。普通的根/内核更新不写加载器固件。当前验收不包含任何 OTP 或熔丝变更。各板卡的证据和限制见
[支持层级](../hardware/README.md#当前板卡)。

## 5. I1–I4 启动保证阶梯

这些逐级叠加的验收等级按板卡/版本记录，并附带有日期的物理证据。机制层面的软件证明单独列出：

- **I1：**经校验的只读内容、更新/回退和恢复证据。
- **I2：**使用预期信任输入的经认证正常部署获取/安装，以及有意义的反例。
- **I3：**在执行检查的启动阶段之下经认证的内核、DTB/initramfs 和启动策略，并有按板卡的替换/签名拒绝证据。
- **I4：**硬件认证的第一个可变阶段，以及保持该链条的、经验证的调试和恢复策略。

当前代码实现了 I1–I3 的机制，并在开发用的 QEMU/沙箱环境中测试。板卡证据保持保守；cx3576 的物理验收尚未
完成。不声明 I4。[BSP 保证页](../hardware/assurance.md)把这一区分应用到板卡页面和发布措辞上。

## 6. 边界 (d)：静态数据机密性——**[partial]**

**目前已发布的 Mica OS 产品上没有任何静态加密。**机制存在于早期 init 中：签名启动策略开启它的产品会得到
LUKS2 加密的 DATA，启动时由 TPM 2.0 密钥提供者解锁，首次格式化时在设备上生成恢复口令
（`mica-core:docs/mica-core.md` 6.5 节）。它在每个已发布产品上都是关闭的；唯一开启它的镜像是测试通道上的
uefi-x64 GCP 镜像。加密的 DATA 还不支持出厂重置。作为已发布产品当前的限制，明确说明：

- DATA 及其 state/meta 命名空间是普通 ext4。设置、apid 管理员密码哈希、sshd 主机密钥、已授权的 SSH 密钥、
  Wi-Fi 凭据、蓝牙配对密钥以及每台设备的两份明文秘密（`/var/lib/mica/secrets/`，
  `docs/integrate/provisioning.md` 第 2 节）对任何持有该介质的人都可读。
- 确实存在的机密性是针对*在线*和*无特权本地*攻击者的：设置树中存哈希而非明文、由测试断言的 0600/0700
  文件权限，以及管理 API 的遮蔽规则。
- 重刷不会擦除：刷写范围之外的块仍留在介质上，只是不再被引用（`docs/reference/access.md` 第 7 节）。处置或
  转交设备需要擦除介质。

这与第 1 节的公理一致，而不是矛盾。静态加密（及其所需的密钥存储方案）只通过它自己经批准的计划推进；本
文档记录这个限制，以免任何发布材料夸大。

## 7. 边界 (e)：恢复与配置——**[partial]**

原生的试运行回退和受保护的手动回滚恢复一个保留的组件关联。按目录范围的重置在共享事务锁下，依所选层级
保留标识、凭据和生命周期记录。整盘重刷替换系统和 DATA，包括标识。

离线配置从 UEFI ESP 或可移动介质以只读方式暂存一份固定文档。cx3576 的 FIRMWARE 是原始分区，使用可移动
介质。micad 在应用之前校验整份文档和已认领策略。它不改动携带凭据的介质。这条通道不认证签名，不得与签名
部署导入器混淆。

当前板卡都没有声明系统层面的物理在场恢复动作。cx3576 加载器的按键打开 rockusb；它并不授权经 apid 的凭据
恢复。这些需要在场闸门的请求仍会被拒绝。尚未实现强制门户/串口配置向导。出厂重置会重建 DATA
（[恢复](../operate/recovery.md)）；它不是经认证的擦除。见[配置](../../integrate/provisioning.md)和
[恢复](../operate/recovery.md)。

## 8. 边界 (f)：以 root 运行的应用和容器——**[implemented]**，附明确限制

容器能力自己的文档说得很直白，本文档不得更软：**本设备上的容器以 root 运行**
（`docs/integrate/containers.md`）。没有构建无 root 模式；任何能向 micad 声明容器、或写入 DATA 上的
`container` 文档的东西，都以 root 的权限运行代码。同样，`mica-unit` 安装的用户服务是 DATA 上 root 可写的
文件（`docs/integrate/native-applications.md` 第 10 节），所以启动时运行哪些东西并不由镜像哈希决定。

当前的约束是诚实而不是隔离：该能力默认关闭（`container.enabled = false`），可写的界面只对 root 开放——因此
它们没有授予 root SSH 未曾授予的东西——并且修改可被观察到（micad 的诊断总线注册表；verity 根本身保持密封）。
今天**没有应用沙箱，也没有受管应用的强制执行**；被攻破或恶意的 root 工作负载拥有设备的可变那一半。应用
隔离只通过它自己经批准的计划推进，在它落地之前，任何发布材料都不得暗示容器受到约束。
