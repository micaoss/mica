# cx3576：CX3576-Z / Rockchip RK3576

`cx3576` 是一块**硬件板**，按产品命名，也是仓库里的移植参考板。它的镜像已发布、
刷写流程已实现，但**从未有一块实体板卡启动过它**，而且没有任何套件会启动 FIT 镜像。

现状快照记于 2026-09-20。事实来自英文板卡档案
[`docs/boards/cx3576.md`](../../boards/cx3576.md)、BSP 同步记录
[`cx3576-bsp-sync.md`](../../boards/cx3576-bsp-sync.md) 与
`mica-boards:boards/cx3576/`；状态以[支持层级表](../../boards/support-tiers.md#current-boards)为准。

## 概况

| 项 | 值 |
|---|---|
| SoC | Rockchip RK3576 |
| 架构 | `arm64` |
| 启动链 | BootROM → 厂商 DDR/SPL/TF-A → 固定版本的 Mica OS U-Boot → **必须验签的 FIT 配置** → 内核与认证的 native init → SYSTEM → 签名的 verity root/support → systemd |
| 固件形态 | `rockchip-loader`（U-Boot 写在镜像第 64 扇区，在镜像内） |
| 分区 | FIRMWARE / SYSTEM / DATA |
| 存储介质 | eMMC `/dev/mmcblk0`（具体型号仍是待测项） |
| 内核 | `armbian/linux-rockchip`，`rk-6.1-rkr5.1`，6.1.115，按提交固定 |
| U-Boot | 主线 v2026.07（`ece349a`），加一个 rockusb 补丁与恢复键的设备树追加 |
| 发布目标 | 是 |
| 支持层级 | bring-up |
| 启动保证等级 | I1 |

启动链里有厂商 blob：DDR init `v1.12` 与 TF-A `bl31 v1.24`（来自 Rockchip `rkbin`）。
软件层面的 FIT 强制验签**不能**证明这两个可变启动阶段被硬件认证过。

## 硬件与功能状态

`BOARD_FEATURES="wifi bluetooth display status-led can usb-gadget containers"`。
“声明”指板卡声明了该特性并带着对应的包与初始化逻辑；实机行全部未测。

| 功能 | 状态 | 说明 |
|---|---|---|
| 容器（Podman） | 随镜像发布 | — |
| Wi-Fi | 已声明，实机未测 | 板子是双 SKU：AP6275S（bcmdhd/SDIO）或 AIC8800D80，构建期不区分。**只带了 AIC8800D80 的固件，AP6275S 不在本档案的声明范围内** |
| 蓝牙 | 已声明，实机未测 | 与 Wi-Fi 同一模组 |
| 以太网 | 已声明，实机未测 | Motorcomm YT8531 PHY，内核补丁带着它的初始化序列；MAC 地址由 eMMC CID 与端口在总线拓扑中的位置派生，而不是取自 machine id |
| HDMI 显示 | 已声明，实机未测 | 输出与旋转的默认值记在板卡定义的说明里，镜像流水线目前不读任何显示设置 |
| 开机 logo | 已实现 | Mica OS 图标加字标，构建时渲染 |
| CAN | 已声明，实机未测 | `hwinit` 的一项 |
| USB OTG / USB gadget | 已声明，实机未测 | gadget getty 的 udev 规则随包发布 |
| 状态灯 | 已声明，实机未测 | — |
| RTC | **存在性未确认** | 设备树声明 `i2c7` 上 `0x51` 的 `AT8563`/`hym8563`，`board.env` 不记录 RTC 事实；驱动与后备电池都没在整机上跑过。时间管理不依赖它：常开 NTP、DATA/state 上的时钟下限与时区设置在完全没有 RTC 的板子上也一样 |
| 物理恢复动作 | 无 | `BOARD_RECOVERY_ACTIONS=""`。**恢复键不是物理在场断言**——它只把板卡送进 rockusb loader 模式，没有任何软件恢复流程读它 |

硬件初始化项（`BOARD_HWINIT_CONFS="otg can bt mac gadget modules"`）各有一个 unit 加
一个脚本，板卡包共使能 6 个 unit。

## 分区布局

| 分区 | 范围 | 说明 |
|---|---|---|
| `FIRMWARE` | 扇区 64–36863（18 MiB 之前） | 内含 U-Boot（第 64 扇区，字节偏移 32768 处魔数 `RKNS`）与两份 64 KiB 带 CRC 的启动记录（16 MiB、17 MiB） |
| `SYSTEM` | 18 MiB 起，1024 MiB | ext4 + verity，不可变组件文件与两份签名部署 |
| `DATA` | 1042 MiB 起，出厂 256 MiB | 首次启动扩展到介质大小 |

完整出厂镜像 1299 MiB = 1 362 100 224 字节（含 GPT 尾部）。GPT 覆盖引导器与两份记录，
所以 DATA 增长不会把它们吃掉。

## 控制台

串口 `ttyFIQ0`，**1500000 波特**，`earlycon=uart8250,mmio32,0x2ad40000`；
`net.ifnames=0`。

## 获取镜像

产品是 `cx3576-dev` 与 `cx3576-prod`。`cx3576` 从未受 `uefi` 那三轮启动缺陷影响——
它的板卡名没变过。校验方法见[获取发布版](../user/download.md)。

## 刷机

**镜像自带引导器**：U-Boot 就在镜像第 64 扇区的保护区间内，所以写镜像等于同时写了
引导器——没有单独的 idblock 步骤，也不产出厂商 `update.img`。

走 USB 上的 `rkdeveloptool`（在 `mica-boards` 里）：

```sh
make -C boards/cx3576 flash-mica      # 设备已在 Loader/RockUSB 模式
make -C boards/cx3576 flash-maskrom   # 设备在 Maskrom 模式
```

- 用 `MICA_IMAGE=<path>` 指定镜像，**必须是解压后的 `.img`**：预检断言文件恰好
  1 362 100 224 字节，`.img.gz` 会立刻以 `wrong factory image size` 失败。
- 预检不碰设备：检查大小、两份 GPT、三个分区的范围与标签、`RKNS` 魔数。
- 写完会**回读比对**（`rl 0 36864` 与 `rl 36864 2623488`），两次比较都通过才执行
  `rd` 复位。不一致时不复位，设备停在 Loader 模式，可以立刻重刷。
- **在 `db` 和 `rd` 之间不要断电、拔线或复位板卡。**
- 前置条件：`PATH` 上有 `python3` 与 `rkdeveloptool`，以及 USB 访问权限。macOS 上先
  `make -C boards/cx3576 rkdeveloptool-macos`。

**被证明的是控制流程，不是某块板**：仓库里的测试用打桩的 `rkdeveloptool` 和伪造镜像
驱动整个流程，断言调用顺序、两个回读区间，以及三处各损坏一个字节都能被发现并阻止
复位。面对真实硬件的每一步、进入 Maskrom 的按键或触点序列、非 root 操作者需要的
udev 规则（仓库没提供）、SD 卡启动回退，全部未验证。细节见[刷写](../user/flashing.md)
第 5 节。

## 首次启动

DATA 扩容、出厂两份部署、健康门确认，与 UEFI 板一致；区别是启动记录放在固件区域内
冗余的 U-Boot 环境里（`tries = 3`），而不是 ESP 上的 loader 条目。

U-Boot 在访问 eMMC 之前就启动看门狗，校验当前 GPT 几何，选记录、写入、刷盘、回读
递减后的尝试次数，然后才加载 FIT；**持久化失败就拒绝启动**。两份记录都耗尽或无效时
进入本地 rockusb 恢复。

## 更新

发布 `full`、`root`、`kernel` 三种归档，与其它板一样。A/B 是 SYSTEM 上的两份文件式
部署，不是分区槽，所以没有“另一个槽”可刷。见[更新包](../user/update-packages.md)、
[更新与回滚](../user/update-rollback.md)。

**注意**：这块板的镜像从未被任何东西启动过，因此整条“写入 → 首次启动 → 更新 → 确认
→ 回滚”的链路在这块板上没有一次端到端执行记录。

## 恢复

阶梯与别的板相同，差别在最底下两级：

- 可用：只读诊断、手动回滚、配置重置、应用数据重置、整盘重刷。
- **不可用**：凭据恢复与恢复出厂——`BOARD_RECOVERY_ACTIONS=""`，物理在场断言产不出来。
- **兜底**：rockusb（上电时按恢复键、启动失败时自动落入），loader 区本身没了就用
  Maskrom，然后 `flash-maskrom` 整盘重写。代价是全部分区**以及设备身份**。
- 安全擦除不存在，eMMC 上没有任何被验证过的擦除原语。

见[恢复](../user/recovery.md)。

## 已知限制

- 实机启动、eMMC 断电、看门狗接管与复位原因、完整 USB 刷写、RTC 与外设合格，全部
  需要一台具名的本地台架设备。
- DDR init 与 TF-A 是厂商 blob；软件 FIT 强制验签不证明首批可变启动阶段被硬件认证，
  也不证明调试通道是关闭的。
- 已接受的射频包针对 AIC8800D80；AP6275S SKU 未合格。
- 确切的 eMMC 型号与板卡版本仍需实物证据。
- `rkbin` blob 与厂商 MiniLoader 的独立 sha256 摘要**未归档**（intake 规则要求二进制
  输入有这个），已记为已知限制。
- 开发用的启动/内容/元数据密钥是独立测试输入，没有任何 OTP/熔丝改动或生产密钥仪式。
- 串口控制台上的 U-Boot 仍是交互式的（`BOOTDELAY=1`，带 `fdt`、`md`/`mw`、`go`），
  能接触串口的人可以改内存里的控制 DTB 或跑未签名的二进制。

## 验证记录

绑定条件（具名版本规则）：板卡版本 CX3576-Z；存储 eMMC `/dev/mmcblk0`，型号未具名；
射频模组 AIC8800D80；BSP 为上游同步 `5e2b1c3` 加本仓库的树。

英文档案里**每一条硬件相关行都是 `not tested`**：冷启动、热启动、A/B 切换与更新、
更新中断电、存储增长与健康、网络与射频、USB/现场总线、RTC、温升、看门狗与复位原因、
离线服务、恢复、安装与首次启动。

存在的是台下（off-hardware）的检查，它们只为自己那一面作证，永远不算实机通过：
原生记录解析与固件 IO（`make os-fit-records-test`）、repart 增长逻辑
（`make os-repart-test`）、刷写控制流程的打桩测试、FIT 签名与密钥轮换的拒绝用例。
