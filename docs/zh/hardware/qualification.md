# 现场可靠性验收

验收是板卡获得声明资格的方式：一个固定的、与可靠性相关的行为矩阵，每一项都在真实硬件上证明（或如实地
保持未证明），并带日期和证据记录在板卡页面的"验收结果"一节中。它把"能启动的镜像"与受支持的产品区分开——
[支持层级](README.md#支持层级)正是建立在这一区分上。下文是流程和行的写法；结果是板卡的事实，记录在各板卡
页面中；[板卡状态表](README.md#当前板卡)列出哪些板卡有物理测试行。

> status: shipped — evidence: `docs/hardware/board-template.md`
> status: board-dependent — evidence: `docs/hardware/cx3576.md`, `mica-build:boards/cx3576/evidence.json`

## 1. 具名版本规则

结果只绑定到以下各项的唯一组合：

- 板卡版本（厂商的版本标记），
- 存储器件（具体的 eMMC/SD/NVMe 型号，而不是技术类别），
- 无线模块（具体 SKU，适用于有无线变体的板卡），
- BSP 版本（同步到的上游提交，加上 Mica OS 树自身的版本）。

结果**从不推广**到其他版本、存储型号、无线模块、散热方案或厂商 BSP。新的组合有新的矩阵；旧矩阵为当初随其
出货的设备保留在案。正因为这条规则，板卡页面的"验收结果"一节要写明其绑定的组合以及它不覆盖的变体。

## 2. 行的写法

每一行只能是以下四种结果之一：

- `pass`——流程在具名组合上运行并满足其标准。带 ISO 日期（`YYYY-MM-DD`）和证据说明：运行了什么、日志/制品在
  哪里。
- `fail`——流程运行了但未满足其标准。带 ISO 日期和证据说明。`fail` 行在修复后不会消失；它由之后带日期的
  `pass` 取代。
- `N/A`——该行不适用于这块板卡（没有无线、没有现场总线），附一行原因。`N/A` 是关于硬件的陈述，从不是关于
  缺少时间或缺少测试台。
- `not tested`——该行适用但尚未运行，附一行原因。在有人运行之前，这是每一行诚实的默认值。

**从不默认通过。**缺失的行、空的单元格或没有日期的 `pass` 是板卡页面的缺陷，不是证据。没有硬件的文档作者
不能、也不会关闭证据行。

建议的表格形式：

| 行 | 结果 | 日期 | 证据/原因 |
|---|---|---|---|

## 3. 矩阵的各行

固定的行集合。"按适用"的行在没有相应硬件的板卡上为 `N/A`（附原因）；其他任何行都不得删去。

| # | 行 | 证明什么 |
|---|---|---|
| 1 | 冷启动 | 从冷态上电可重复地进入健康系统（健康闸门通过） |
| 2 | 热启动 | 从运行中的系统重启可重复地进入健康状态 |
| 3 | A/B 切换与更新 | 签名组件文件被持久发布，候选启动并通过健康确认；三次失败的试运行选择保留的部署且不重新填充 |
| 4 | 更新中断电 | 安装过程中断电后，设备可启动进入之前已提交的部署；反复断电不会变砖 |
| 5 | 存储增长/健康 | 数据分区在首次启动时增长；bulk/可丢弃部分的字节和 inode 配额保住必要的 state/meta 容量；存储健康读数可用 |
| 6 | 网络/无线 | 以太网和每个具名无线模块在随附的协议栈下关联/传输 |
| 7 | USB/现场总线（按适用） | 在随附的 hwinit unit 下的 USB 主机/设备角色和现场总线（如 CAN）通信 |
| 8 | RTC | 时间在断电后保留（有电池），或者对没有 RTC 的情况有处理（有文档的重新同步行为） |
| 9 | 温度/降频 | 持续负载保持在热设计范围内；降频只降低性能，不导致崩溃 |
| 10 | 看门狗/复位原因 | 挂起的系统被看门狗复位；之后能读出复位原因 |
| 11 | 离线服务 | 按配置模型，设备在没有网络的情况下完全可用、可配置 |
| 12 | 恢复 | 板卡页面"恢复"一节中的每条恢复路径，确实能把设备从它声称能处理的状态中恢复 |
| 13 | 安装与首次启动 | 文档中的刷写流程能通过板卡自己的通道把镜像写到空白设备上，该设备能完成首次启动并进入可认领状态 |

**第 13 行除版本外还绑定配置档。**其余十二行绑定第 1 节的组合；安装还要针对两种镜像之一（`dev` 或 `prod`）
来测试，因为写入的镜像必是其中之一；没有配置档软件包，两者的区别在于签名内核命令行参数 `mica.profile`。证据
说明要写明配置档，声称两者都支持的板卡要运行两次，或说明哪一个尚未证明。这一行也覆盖流程放到介质上的任何
离线配置文档："首次启动"指设备以流程所声称的状态启动，而不只是上电。

第 3、4、12 行决定了一块板卡是*受支持*而不只是*能启动*：BSP 契约的新板卡清单以断电测试台运行结束，原因相同；
没有带日期的第 3/4/12 行的板卡，不论其余各行如何，都不能成为 mica 验收的板卡。

## 4. 证据标准

- 硬件行需要硬件。只有当该行的声明确实关于被测的界面时，主机侧或 QEMU 闸门才能支持 `pass`——例如 U-Boot
  握手逻辑有脱离硬件的测试套件，那是关于脚本逻辑的证据，而不是台架上第 3 行的证据。证据说明必须写明是哪一种。

> status: shipped — evidence: `mica-build:make os-fit-records-test`

- 证据说明要给出位置：日志路径、测试台运行 ID、链接的记录。没有制品的"在我的台子上能用"就是多说了几句的
  `not tested`。
- 可重复性很重要：冷/热启动行要写明循环次数。

## 5. 重新验收的触发条件

当任何绑定要素变化时，矩阵就会过期——其各行对新组合回到 `not tested`：BSP 同步到新的上游提交、内核或引导
加载器升级、新的存储型号或无线 SKU、新的板卡版本。主题不受变更影响的行只能作为板卡页面中明确的、带日期的
决定被沿用（"沿用 <日期> 的运行；判断该变更无关，因为……"），从不悄悄沿用。

## 6. 谁来运行

按[支持层级](README.md#支持层级)：对 mica 验收的板卡，由 Mica OS 负责运行和证据；对集成方验收的板卡，由
集成客户负责两者，Mica OS 的声明相应更窄。两种情况下，写法和矩阵都以本文为准——可比的证据正是目的所在。
