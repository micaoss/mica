# s905x5m：BM201 / Amlogic S905X5M（S7D）

`s905x5m` 是一块**硬件板**。它自 2026-09-19 起是发布目标，镜像会像其它板一样发布——
但**今天没有任何受支持的办法把 Mica OS 装进一块空板**，原因是固件位置，见下面的
“刷机”。

现状快照记于 2026-09-20。事实来自英文板卡档案
[`docs/boards/s905x5m.md`](../../boards/s905x5m.md) 与 `mica-build:boards/s905x5m/`；
状态以[支持层级表](../../boards/support-tiers.md#current-boards)为准。

## 概况

| 项 | 值 |
|---|---|
| 硬件 | X88 Pro X5M / BM201 开发单元 |
| SoC | Amlogic S905X5M（S7D） |
| 架构 | `arm64` |
| 启动链 | eMMC boot0 里的 Mica OS Amlogic 固件 → 选中 SD 系统盘（`mmc 0`）→ **必须验签的 FIT**（公钥嵌在最终导出的 BL33 控制 DTB 里）→ 签名内核与认证的 native init → SYSTEM → 签名的 verity root/support → systemd |
| 固件形态 | `amlogic-boot0`（U-Boot 在 eMMC boot0，**不在镜像里**） |
| 分区 | FIRMWARE / SYSTEM / DATA（在 SD 上） |
| 内核 | `hardkernel/linux`（`9ea2aa83`），含 14 个本地补丁、板卡 DT 与 Seekwave 源码 |
| U-Boot | `CoreELEC/u-boot`（`5f7ac2b1`），补丁 0001–0007 与 0019–0020 |
| 发布目标 | 是（自 2026-09-19 的用户决定；首个发布 `s905x5m.20260920-0033`） |
| 支持层级 | bring-up |
| 启动保证等级 | I1（不声称硬件级启动保证） |

自动启动会给 Meson 看门狗上 60 秒；看门狗为用户态喂狗模式，驱动在设备注册前应用
NOWAYOUT。启动路径不导入任何 U-Boot 环境或启动脚本。

## 分区布局（SD 卡）

| 分区 | 范围 | 说明 |
|---|---|---|
| `FIRMWARE` | 扇区 64 到 128 MiB | **不含 SD 引导器**：只有两份 64 KiB 启动记录（绝对 120 MiB 与 124 MiB）与填充 |
| `SYSTEM` | 128–1152 MiB | ext4 + verity |
| `DATA` | 1152 MiB 起，出厂 256 MiB | 只有它增长 |

eMMC boot0 里的固件由一份签名的外部固件回执描述：厂商生成的 512 字节头之后，载荷
上限 4 193 792 字节。原生回读能独立于 SD 系统盘找到 eMMC 硬件启动分区。普通的
root/kernel 更新**不写固件**。

## 控制台

串口 `ttyS0`，**921600 波特**，`earlycon=aml_uart,0xfe07a000`。
**接线前先对照具体板子的硬件记录确认接口与电平。**

## 获取镜像

产品是 `s905x5m-dev` 与 `s905x5m-prod`，自 `s905x5m.20260920-0033` 起发布。
**发布了不等于能装**：见下一节。

## 刷机

**今天没有受支持的安装路径。**

原因在固件位置：Mica OS 的 U-Boot（`u-boot.bin.signed`）从 eMMC boot0 区域执行，
前面是目标端生成的 512 字节 Amlogic 头；来源不是 boot0 时 loader 拒绝自动启动。
而发布的磁盘镜像只覆盖 SD 介质（第 64 扇区起的 FIRMWARE、SYSTEM、DATA），**把它写到
卡上不会装上任何引导器**。只有 boot0 里已经带着配套 Mica OS U-Boot 的板子，才能从这
张卡启动。

朝着未来流程已经有的东西：

- `make -C boards/s905x5m uboot` 构建签名的 U-Boot 及其 DDR 固件。
- `make -C boards/s905x5m uboot-package` 构建 Amlogic v2 `update.img`（固定版本的
  `aml_image_v2_packer`，通过再次解包校验），以 `bootloader.PARTITION` 携带签名的
  U-Boot，并**有意省略** `gpt.bin` 与 `bootloader_a`，使烧录只框住硬件启动区域、
  碰不到用户区 GPT。

缺的是：哪个主机工具消费这个镜像、boot0 如何写入与回读、变砖的板子如何恢复——既没
写下来也没测过，属于 `mica-boards` 与 `mica-build` 共同拥有的台架工作。
见[刷写](../user/flashing.md) 第 6 节。

> status: unsupported

## 首次启动

与其它 FIT 板一致：一秒的原生控制台倒计时不消耗尝试次数；自动启动上看门狗、选一条
有界的原生记录、持久化并回读尝试次数，然后验签 FIT。DATA 在首次启动扩展。
这些都没有在实机上执行过。

## 更新

发布 `full`、`root`、`kernel` 三种归档。普通更新不触碰 eMMC boot0 里的固件——固件维护
是独立的签名 + 回读流程，而通用的 Mica OS 固件维护**刻意拒绝**这个硬件启动目标。
见[更新包](../user/update-packages.md)。

**这棵树里没有任何东西会启动这块板的镜像**（没有套件会启动 FIT 镜像），所以更新链路
在这块板上没有端到端记录。

## 恢复

- 可用（在一台已经能启动的设备上）：只读诊断、手动回滚、配置重置、应用数据重置。
- **不可用**：凭据恢复、恢复出厂——不声明物理恢复动作。
- **兜底**：Amlogic USB 烧录模式（板卡的 `aml_sdc_burn` 流程与它的 `update.img`
  容器）。这条路对任何有物理接触的人开放，它同时也是这块板被记录在案的物理访问
  边界。实际的安装与恢复仍需台架合格。
- 安全擦除不存在。

见[恢复](../user/recovery.md)。

## 已知限制

- SD 启动要求 eMMC boot0 里有配套的 Mica OS 固件；原厂固件不实现这套签名文件策略。
- 不提供兼容读取器、历史布局安装器，也不做既有状态迁移。
- 不透明的 Amlogic 阶段与射频固件保留其可审计性与分发许可的限制。
- 当前 CI 下不能执行原生 crun（BuildKit/QEMU 跑不了它的 memory-file re-exec）。
- 没有任何实机行被记录；`RFCT-922`（用受控对端跑蓝牙配对与一个 profile）仍开着。
