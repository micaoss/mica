# s905x5m：BM201 / Amlogic S905X5M（S7D）

`s905x5m` 是一块**硬件板**。它的镜像和其他板一样被构建与验证，但**安装或启动它的任何
一步都没有在实机上留下记录**：本页每一条关于实机的陈述都未经验证。

这块板有两种存储布局。`s905x5m.basic` 与 `s905x5m.emmc-full` 把系统放在 eMMC 上，连同
加载器一起，以 USB 烧录包的形式整体安装。`s905x5m.sd-full` 把系统放在 SD 卡上，并要求
板子的 eMMC boot0 里有匹配的 Mica OS U-Boot，它的发布把这个 U-Boot 作为第二个包一并带上。

状态以[状态表](README.md#当前板卡)为准。

## 概况

| 项 | 值 |
|---|---|
| 硬件 | X88 Pro X5M / BM201 开发板 |
| SoC | Amlogic S905X5M（S7D） |
| 架构 | `arm64` |
| 启动链 | eMMC boot0 里的 Mica OS Amlogic 固件 → **必需的签名 FIT**，其公钥嵌在加载器的控制 DTB 里 → 签名内核与认证的 native init → SYSTEM → 签名的 verity root/support → systemd |
| 固件形态 | U-Boot 在 eMMC boot0 里，**从不在磁盘镜像里** |
| 分区 | FIRMWARE / SYSTEM / DATA，在 SD 上或 eMMC 用户区上 |
| 内核与 U-Boot | 厂商树，连同补丁固定在 `mica-build:boards/s905x5m/bsp.env` |
| 支持层级 | bring-up |
| 启动保证等级 | I1；不作硬件信任根声明 |

U-Boot 之前有不透明的 Amlogic 阶段。自动启动在消耗一次尝试之前先启动 60 秒的 Meson
看门狗，不导入任何 U-Boot 环境或启动脚本。

## 分区布局

在 SD 上（`sd-full`）：

| 分区 | 范围 | 说明 |
|---|---|---|
| `FIRMWARE` | 扇区 64 到 128 MiB | **不含引导加载器**：两份 64 KiB 的启动记录在 120 与 124 MiB 处，其余为填充 |
| `SYSTEM` | 128–1152 MiB | ext4 + verity |
| `DATA` | 自 1152 MiB 起，出厂 256 MiB | 唯一会扩展的分区 |

在 eMMC 上（`basic`、`emmc-full`），与厂商自己的分区并存，厂商分区保留不动：

| 分区 | 范围 | 说明 |
|---|---|---|
| `firmware` | 128–136 MiB | 两份启动记录 |
| `system` | 136–1160 MiB | ext4 + verity |
| `data` | 自 1160 MiB 起，出厂 256 MiB | 唯一会扩展的分区 |

权威几何在 `mica-build:boards/s905x5m/layout.tsv` 与
`mica-build:boards/s905x5m/layout-emmc.tsv`。普通更新从不写 boot0 里的固件。

## 刷机

**写入 eMMC（`basic`、`emmc-full`），未验证。** USB 烧录包是给厂商 USB Burning Tool 用的 Amlogic
v2 烧录镜像。它写入分区表、两个 bootloader 目标、厂商设备树和 Mica OS 的三个分区，不动
厂商的其他分区。上电时按住恢复键，板子进入 USB 烧录模式。构建会解包自己生成的每一个
烧录包，并证明每个载荷都与其来源一致；还没有人把它烧到实机上。

**写入 SD（`sd-full`），未验证。** 把解压后的磁盘镜像写到整张卡上。**写入它并不会安装
引导加载器**：镜像只覆盖 FIRMWARE、SYSTEM 与 DATA，只有 eMMC boot0 里已经有匹配的
Mica OS U-Boot 时，板子才会从这张卡启动。它就是同一个发布里镜像旁边的引导加载器包，
一个 USB 烧录包，经同一种 USB 烧录模式安装
（`mica-build:boards/s905x5m/loader/README.md`）。

细节见[刷写](../start/flashing.md)第 6 节。

> status: unsupported

## 首次启动

先是一秒的控制台倒计时，不消耗尝试次数；然后启动看门狗、选择一条启动记录、把这次尝试
落盘并回读，再验证 FIT。DATA 在首次启动时扩展。这些都没有在实机上跑过。

## 更新

发布 `full`、`root` 与 `kernel` 归档，core 发布时还有 `core`。普通更新从不触碰 eMMC boot0
里的固件，通用的固件维护也有意拒绝这块板的启动目标。见
[更新与回滚](../operate/updates.md)。

这些仓库里没有任何东西启动这块板的镜像，所以更新路径在这里没有端到端的记录。

## 恢复

- 能启动的设备上可用：只读诊断、手动回滚、配置重置、应用数据重置。
- **不可用**：凭据恢复与恢复出厂，因为没有声明物理恢复动作。
- **兜底**是 Amlogic USB 烧录模式，上电时按恢复键进入。任何能接触到设备的人都能进入，
  这也是这块板记录在案的物理访问边界。代价是所有分区和设备身份。
- 没有安全擦除。

见[恢复](../operate/recovery.md)。

## 已知限制

- SD 启动要求 eMMC boot0 里有匹配的 Mica OS 固件；原厂固件不实现签名文件策略。
- 不透明的 Amlogic 阶段与射频固件保留其可审计性与分发许可上的限制。
- 加载器无法逐字节重现构建，因为厂商的签名步骤不是确定性的。
- 没有任何实机行在案，与受控对端的蓝牙配对未测试。
