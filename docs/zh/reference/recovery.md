# 恢复与重置

恢复从诊断和保留的签名部署开始。重置改变可写命名空间；它不修复 SYSTEM，不替换内核，也不撤销任意的应用数据
变更。所有开发验收都从一份完整的当前镜像开始。

## 1. 故障边界

原生 UEFI/FIT 启动记录限制候选的尝试次数，并保留一个可用的已确认回退。耗尽或失败的部署不会以补满的计数器
被悄悄重试。共享的 SYSTEM 或 DATA 故障需要明确的恢复；切换根无法修复共享的文件系统。

见[更新](updates.md)、[存储](storage.md)和[启动契约](boot.md)。固件替换是独立的
[维护操作](../security/signing.md)。

## 2. 重置层级

### 2.1 范围与保留项

API 和 `micad_settings::ResetTier` 恰好提供两个层级。执行者是 `mica-core:crates/micad/src/reset.rs`。出厂重置
不是一个层级：它有自己的路由（2.3）。

| 层级 | 删除或重新播种 | 保留 |
|---|---|---|
| `configuration` | `/mica/config`、板卡默认值的播种记录（因此默认值会回来）和 apid 的 HTTPS 身份；建模的设置通过首次启动配置回来 | 设备标识和秘密、管理凭据/认领/API 令牌、容器和运维数据 |
| `application-data` | `/mica/volumes`、容器引擎的存储和项目、DATA/state 中的 `containerd`、`systemd-units` 和 `openrc-local`（用户的服务）以及 `accounts`（服务账户，会重新构建） | 设置、标识、凭据、自定义 UI、`/srv`、更新工作区和其他系统命名空间 |

每个层级都保留 SYSTEM、启动记录和 DATA/meta 的生命周期/部署状态。没有层级打开 `/srv`，也没有层级跨进挂载：
被清除的树中有东西挂在上面的目录（例如挂在容器存储上的用户磁盘）连同其下的一切保持不变。`/run/docker.pid`
指向一个存活的 `dockerd` 时，`application-data` 会被拒绝。删除白名单之外的校准数据保持不动。机器 ID 和其他
被保留的服务文件不会作为新的身份重新生成。

配置重置清空整个公开配置目录，包括没有作为建模设置表示的文档。应用重置连同载荷一起删除 unit 的登记。配置
重置把配置标记为待处理，以便正常的初始化程序从保留的设备标识重新建立默认值；没有要读取的镜像配置档
（`docs/reference/access.md` 第 8 节）。

### 2.2 意图、执行与中断

`apid` 授权所请求的层级，并在设置树中暂存一个持久的重置意图。下一次 `micad` 启动时，在正常调和之前应用该
层级。执行者校验物理的 DATA/state 路径，拒绝符号链接的根和嵌套挂载，并获取安装所用的同一把事务锁。遍历在
深度、条目数和耗时上都有界。

删除使用该层级的白名单，并同步发生变化的目录。清除意图的设置保存最后进行。失败或被中断的应用保留其意图并
以相同范围重试；从不升级为更宽的层级。成功之后重复启动是幂等的。

配置重置和应用数据重置需要经认证的管理权限。

### 2.3 出厂重置

出厂重置清除所有配置过的东西，保留运行中的软件。

- **谁来请求。**`POST /api/v1/system/factory-reset` `{password}`、控制台的系统页，以及设备上 root 运行的
  `mica factory-reset`。API 和控制台不论调用方的凭据如何都要求管理员密码，错误的密码计入登录退避（连错
  3 次后，每次把等待时间从 5 秒加倍到 300 秒）。设备上的 root 不需要密码：`mica factory-reset` 先列出会清除
  什么、保留什么，然后等待输入主机名或 `factory-reset`，或者带 `--yes`；两者都没有、或没有终端时，什么也不
  重置。micad 以代码拒绝
  （409）：DATA 已加密（启动程序不重置加密的 DATA）时为 `data_encrypted`；启动的 runkit 不执行重置时为
  `factory_reset_unsupported`；未认领的设备为
  `not_claimed`；`update_in_progress`；部署或集合在试运行时为 `trial_pending`。
- **暂存。**设备必须运行一个已确认的部署；待确认的候选会被拒绝。请求以及描述 SYSTEM 的 DATA `meta/` 文件
  快照（固件回执、目录检查点、部署状态）暂存在 SYSTEM 上，快照先写，设备在 3 秒后重启。
- **清除什么。**runkit 重建 DATA 而不是清空它：`gpt` 板卡按板卡的 `dataFormat` 用根的 `mke2fs` 重建，`ubi`
  板卡清空 `data` 卷；无法重建的 DATA 会就地擦除。因此 STATE 及其中的设置、认领、API 令牌、密钥、SSH 主机
  密钥和 machine-id、容器、用户的服务、`/srv`、`/mica` 以及保存在那里的日志都会消失。随后它恢复快照。根的
  第一次启动在 SYSTEM 上完成重置（`micad` 在其他任何事情之前运行 `mica-deploy factory-reset --finish`）：它
  删除运行中部署之外的所有部署和 core 集合（连同只有它们持有的对象），以及所有驱动扩展和已登记的 owner 证书，
  最后删除请求，所以在此之前任何地方的中断都会在下次启动时再次执行重置。
- **保留什么。**运行中的部署及其 core 集合（所以软件版本不变）、启动记录、用户自己的磁盘，以及从硬件派生的
  设备码（`random` 设备码的种子在 DATA 上，会重新生成）。设备回到未认领状态，开启出厂接入点并使用标签上的
  密钥，首次启动会生成新的设备 id、主机名、machine-id 和 SSH 主机密钥。
- **之后。**那次启动会记录这次重置（`GET /api/v1/system/factory-reset` 的 `last`，DATA 被重建时带
  `formatted`），并在文件系统和介质允许时丢弃 DATA 的空闲空间（UBIFS 上不做，不支持 TRIM 的卡上不做）。它
  不是经认证的擦除（第 7 节）。
- **没有 micad 时。**root 运行 `mica-deploy factory-reset [--reboot]` 暂存同样的重置
  （[没有 micad](../operate/without-micad.md) 第 7 节）；`--cancel` 删除已暂存的重置。

> status: board-dependent — evidence: `mica-core:crates/micad/src/factory_reset.rs`, `mica-core:crates/mica-apid/src/routes/reset.rs`, `mica-core:crates/mica-deploy/src/factory_reset.rs`, `mica-core:docs/mica-core.md`

## 3. 运维顺序

1. 采集控制台日志和经认证的部署状态。API 在运行时，采集其有界的诊断快照和存储观测。
2. 让原生试运行耗尽以选择可用的回退，或通过 API 请求一次符合条件的回滚并另行重启。
3. 在运行中的系统和存储支持该操作时，修正配置或安装新签名的更高代数部署。
4. 只有当重置的文档化数据范围能解决故障时才使用重置。在授权的破坏性操作之前保存需要的运维数据。
5. 对于无法启动的共享存储或耗尽的部署，在外部服务主机上诊断，或刷写完整的当前镜像。整盘重刷会替换介质内容，
   不是保留数据的修复。

## 4. 物理在场

板卡声明 `BOARD_RECOVERY_ACTIONS` 描述可用的机制。运行时的在场闸门要求一个受支持的、有界的声明，并为授权的
操作消耗它。它独立于普通认证，从不根据 API 调用方声称自己站在设备旁边来推断。

当前板卡都没有声明经过验收的系统恢复动作。因此需要在场闸门的凭据恢复在正常的现场 API 上会被拒绝。可用的
固件控制台或 RockUSB 加载器通道本身并不构成系统层面的在场声明。在宣传这一能力之前，板卡验收必须确立物理
动作、交接、过期和一次性使用的行为。

## 5. 凭据恢复

恢复在在场闸门下替换凭据；它从不回读密码或私钥。凭据轮换和重置是不同的操作。审计记录记下结果而不暴露秘密
材料。普通的登录失败无法通过重启清除持久的暴力破解计数器。恢复专用的计数器行为与凭据路由一起测试。

认证、认领和首台设备标识的归属见[访问](access.md)和[配置](../integrate/provisioning.md)。

## 6. 无法启动的系统

### 6.1 部署耗尽

当没有可用的经认证启动记录时，UEFI 和 cx3576 会停止。连同控制台日志一起采集原生条目或冗余的 FIT 记录。没有
未签名的逃生路径或计数器补满来掩盖故障。

### 6.2 共享存储修复

启动时有界的日志重放不是通用的文件系统修复服务。Mica OS 不提供独立的救援系统或自动的保留数据修复操作。外部
诊断和完整的当前镜像重刷仍是明确的服务操作；两者都不会因为 A/B 而获得数据保留的保证。

### 6.3 应急 shell 工具

应急 BusyBox 可执行文件位于同一个经认证的根中。它是根能够挂载时的诊断工具，而不是针对损坏的根或不可用的
SYSTEM 的独立恢复环境。

## 7. 数据清除

没有安全擦除的重置层级，出厂重置也不是。新文件系统和删除文件一样，并不能证明数据已从闪存重映射、备用块或
外部备份中移除。重置或整盘刷写都不意味着任何板卡层面的擦除验收。

## 8. 验收证据

uefi-x64 QEMU 覆盖签名启动、健康确认、试运行耗尽、panic/看门狗回退、出厂重置和完整关机。中断重置的测试在
一次成功删除后杀掉真实的重置执行者，然后对每个层级验证重试、范围保持以及又一次幂等的启动；用户存储阶段检查
没有层级跨进用户的挂载。

cx3576 有离线镜像/FIT 校验和固件策略测试。其物理启动、看门狗交接、恢复和断电行为需要
[台架手册](https://github.com/micaoss/mica/blob/9dd6302/docs/boards/cx3576-bench.md)。启动保证与恢复能力是两项
独立的声明。各板卡待完成的检查见[支持层级](../hardware/README.md#当前板卡)。
