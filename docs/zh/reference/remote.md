# 设计：远程管理与 API 面

> 谁能访问设备、经由什么、以何种信任。**[已实现]** 表示代码存在并按路径指出；**[未实现]** 表示只有文字。

## 1. 今天能访问设备的是什么：**[已实现]**

**apid，在局域网上。**apid 是 micad 的可执行文件以 `mica-apid` 为名运行，在 micad 的 core 组件中，两种 init
上都启用。它在 `access.web` 设置指定的地方监听（`GET`/`PUT /api/v1/web`，控制台的访问页）：默认在
`0.0.0.0:8080` 上提供普通 HTTP，不提供 HTTPS，因此不占用其他服务的 80 和 443。开启 `httpsEnabled` 后，它在
`httpsPort`（默认 8443）上用每台设备自签名的身份提供 HTTPS，运维者可以上传证书链替换它，此时 HTTP 端口只做
重定向；会话 cookie 恰在此时带 `Secure`。这是 `network` 模式；`local` 关闭监听器，只留下 root 拥有的套接字
`/run/mica/apid.sock`，`off` 停止 apid。设备上 root 运行的 `micad web` 在每种模式下都能读取和设置模式。没有
其他管理协议或端口（`mica-core:docs/mica-core.md` 第 4 节）。

**API 就是闸门。**apid 在自定义界面包的兜底路由之前保留 `/api`、`/_ui`、`/healthz` 和 `/`
（`mica-core:crates/mica-apid/src/routes`）。静态 SPA 始终可读；设备数据不可读。每个管理 API 处理程序都要求
已保存的 bearer 令牌或签名的浏览器会话，经会话认证的修改操作还要求其随机的 `X-CSRF-Token`。只有初始设置和
会话发现是无需认证的 API 操作；`/healthz` 只证明监听器存活。

**`/api` 下的 JSON API 就是完整的管理协议**：带版本的设置和状态读取、有类型的写入和集合、排队的任务记录、
初始设置和会话生命周期、界面选择、实时网络观测和系统操作。其生成的契约是
`mica-core:crates/mica-apid/openapi.json`。

**apid 不拥有状态；它是 micad 的客户端**，经 D-Bus 通信（`mica-core:crates/mica-apid/src/bus_client.rs`）。
micad 以 `com.mica.micad` 持有设置树；apid 从不派生进程，也从不直接与 systemd 通信。

**SSH 和控制台是接入通道，而不是管理通道**，两者默认都关闭：SSH 关闭，串口控制台没有接受凭据的账户
（[访问](access.md)）。

**不提供由设备发起的管理通道或集群管理面。**没有东西向外拨号，也没有东西登记设备；每条进入的路径都是入站的，
在局域网上。

## 2. 访问 NAT 后的设备：需求

位于别人网络中 NAT 之后的设备必须能被访问以提供支持，集群必须能被管理，而且**不需要入站端口**：端口转发会让
设备要么没有支持方案，要么带上其所有者未曾选择的攻击面。这就要求一条由设备发起的通道：设备向外拨号，管理
沿它打开的连接回传。

## 3. 集群管理：**[不属于已发布的产品]**

Mica OS 不提供集群管理面，没有已发布的镜像会向集群管理面登记。内置的默认值带有一个关闭的 `fleet` 块
（`enabled: false`，没有 `url`），已发布的根中没有任何东西读取它。任何未来的通道都必须遵守第 5 节的不变量。

## 4. 更新的控制流

已实现的路径是：目录检查、获取缺失的对象、暂存经校验的部署、原生安装、重启和健康确认。`mica-deploy` 用签名
内核中的密钥认证每份部署描述符，并把安装与垃圾回收和重置串行化。micad 经 D-Bus 暴露生命周期；apid 和控制台
显示候选、当前和回退的标识，以及获取、安装、重启和确认的状态。

来源是一个更新根，例如 `https://res.micaos.dev/update/`：一份未签名的清单，列出每个产品的当前发布、该发布的
文档及其签名描述符。信任来自描述符：设备只接受自己的板卡、架构和产品，只接受高于其运行代数的代数，只接受
描述符列出的对象。没有通道，也没有过期时间；被扣留的清单读作"没有更新的"。来源是运维者的设置
（`/mica/config/updates.json`），从镜像内置的默认值播种；改变它不能改变签名启动策略中嵌入的锚点。离线
`.micaupd` 导入汇聚到同一个经校验的工作区（`mica-core:docs/mica-core.md` 第 6.2 节）。

`mica-build` 的发布运行把每个发布推送到该根背后的资源服务（`mica-build:README.md`），资源服务提供每个产品的
当前发布。

自动策略使用设备配置的计划、维护窗口和重启策略。重启闸门防止无关的重启丢弃尚未落定的更新；越过它必须明确
指定并会被审计。确切的路由和失败语义见[更新](updates.md)。

没有向外的集群管理连接，也没有远程集群触发。未来的此类连接必须调用同一套经校验的部署策略，不能绕过签名、
板卡、容量、保留回退或重启检查。

## 5. 安全态势

**今天暴露的：[已实现]。**在默认的 `network` 模式下，局域网上 8080（开启 HTTPS 后还有 8443）端口的 apid 就是
全部的入站管理面；`local` 和 `off` 移除它。`/_ui` 和自定义界面资源是该源上公开的静态代码；每个设备操作和数据
都受第 1 节所述的 `/api` 凭据边界保护。

**今天不暴露的：[已实现]，作为构建所断言的缺失。**没有其他入站管理端口，没有向外的管理连接，也**没有预置到
设备上的运维者凭据**。签名的 rootfs 在每台设备上逐字节相同，所以内置在其中的凭据会成为整个集群共享的秘密
（`stages/compose/scripts/pack-assert-shadow-chain.sh`）：打包步骤会因此让构建失败，这个理由也约束任何未来的
集群凭据。

**未来的通道必须遵守的不变量：[未实现]。**每个管理面是独立的凭据域；攻破其中一个，在另一个中得不到任何东西。
apid 会话不是登记凭据，登记凭据不是 root shell，持有集群通道凭据的端点不能因此持有授权镜像的密钥：更新的信任
锚点已经是独立的密钥层级（`mica-core:crates/mica-deploy`），并保持如此。
