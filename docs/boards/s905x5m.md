# Board dossier: s905x5m

## Identity

X88 Pro X5M / BM201, Amlogic S905X5M (S7D), `MICA_ARCH=arm64`.
The board implementation is in `boards/s905x5m/`.

## Provenance

This mainline adaptation imports the board-owned implementation from
`board/s905x5m` at `e53c1cfd`. The current signed-file port builds on mainline
`5c61f7fbb558`.

- Kernel: hardkernel/linux at `9ea2aa831a585955dcb0e38a0bc3c63d2c690adc`,
  with its pinned common_drivers submodule, fourteen local patches, board DT
  and Seekwave sources. Input class: source plus firmware blobs.
- U-Boot: CoreELEC/u-boot at `5f7ac2b1dc4df2f466ed88c3958a8675873f8a1a`,
  with patches 0001–0007 and 0019–0020. The retired installer patches are
  excluded from the build. The public FIT-key tool is backported from U-Boot
  `ece349ade2973e220f524ce59e59711cc919263f`.
  Input class: source plus vendor boot-chain blobs.
- Seekwave userland: board-local vendor library and integration bridge,
  imported with the source branch; provenance and license notices remain in
  `mica-boards:boards/s905x5m/userland/`.
- Amlogic package blobs: BM201 recovery inputs from s905x5m-alpine
  `49618bed07508b77bb8e8e640e0faafc5c95ea9a`; the package blob README and

## Boot chain

The paired Mica OS Amlogic firmware runs from eMMC boot0 and selects the current
SD system disk (`mmc 0`). The one-second native console countdown consumes no
trial. Automatic boot arms the 60-second Meson watchdog, selects a bounded native
record, persists and reads back the attempt, then verifies the selected FIT with
the required public key embedded in the final exported BL33 control DTB.

The signed kernel supplies its forced command line, content certificate and
native init. The vendor watchdog is set to userspace feed mode with a 60-second
DT timeout; the driver applies NOWAYOUT before device registration. Native init authenticates deployment metadata and mounts verified
root/support components. The path imports no U-Boot environment or boot script. Development console access and
opaque vendor stages mean this is not a hardware-rooted assurance claim.

## Storage media and layout

The SD GPT contains FIRMWARE from sector 64 to 128 MiB, SYSTEM from 128 to
1152 MiB, and DATA from 1152 MiB with a 256 MiB factory seed. Only DATA grows.
The two 64 KiB boot records are at absolute 120 and 124 MiB. FIRMWARE contains
records and zero padding; it does not contain an SD bootloader.

The signed external firmware receipt describes the eMMC boot0 payload after its
512-byte vendor-generated header, bounded to 4,193,792 bytes. Native readback
finds the eMMC hardware boot partition independently of the SD system disk.
The firmware and signed receipt remain beside the SD image for offline checks.
Ordinary root/kernel updates do not write firmware. Complete eMMC OS installation
is outside this SD-first milestone.

## Console

The serial console is `ttyS0` at 921600 baud, with
`earlycon=aml_uart,0xfe07a000`. Confirm the connector and voltage against the
specific board's hardware record before wiring. HDMI output depends on the
vendor display initialization and the board kernel/DT.

## Peripherals

The board declares Wi-Fi and Bluetooth using the Seekwave SWT6621/EA6521QF
firmware and SDIO transport. Bluetooth uses the vHCI bridge, not a UART
attach helper. Its derived address persists in protected `DATA/state/bluetooth`, mounted at
`/var/lib/bluetooth` by the shared Bluetooth package; `bdaddr` is stored there; BlueZ uses the hostname plugin for the name.

`BOARD_HWINIT_CONFS` maps audio to ALSA routing, wireless to rail/module
initialization, and Bluetooth to the bridge. The radio packages are selected
independently: declining Wi-Fi retains the shared SDIO transport if Bluetooth
still needs it. Ethernet, HDMI and USB support remain in the kernel/DT and
vendor initialization. No status LED or board recovery action is declared.
RTC retention and the full peripheral matrix need qualification on this image.

The BM201 front panel is an optional local package selected with
`MICA_ROOTFS_COMPONENTS=bm201-front-panel`. Its executable service reads
`/run/mica/timezone` on each update. Declining both radios omits the shared rail
initializer; selecting Bluetooth alone does not load the Wi-Fi driver.

## Recovery method

`make s905x5m-uboot-package` packages the new Mica OS firmware with the pinned
Amlogic recovery inputs and verifies pack/unpack readback. Install/recover the
paired firmware through the board's Amlogic procedure; generic Mica OS firmware
maintenance deliberately refuses this hardware-boot target. No automatic flash
or OS physical-recovery action is advertised. The native console remains
available before boot selection. Actual installation and recovery need bench
qualification; building a recovery package does not establish those results.

## Known limitations

The development image producer is implemented, but `BOARD_RELEASE_TARGET=0`
remains until current physical qualification is recorded. SD boot requires the
paired Mica OS firmware in eMMC boot0; original vendor firmware does not implement
this signed-file policy. No compatibility reader, historical-layout installer
or existing-state migration is provided. Opaque Amlogic stages and radio firmware
retain their recorded auditability and distribution-license limits.

**This board is parked on the user's instruction, and one red job follows from
that** *(2026-09-21)*. It has more to repair than the defect found that day and
gets its own round later. The consequence worth writing down:
`s905x5m.20260920-1536` is still the newest release and still carries a forced
kernel command line that **disagrees with the board's own `board.env`**; the
repair is on `mica-boards` `main` (`e1e8231`, *s905x5m boots the line its
board.env declares*) and is **in no release**. So **`s905x5m-prod` is red on
`mica-build`'s `main` — expected, indefinite, and correct**: the bundle really
is inconsistent and the refusal is right to refuse it. The **second** standing red has since
landed and is named: `os-build-test`, four failures, all four of this board's
kernels — red by a ruling the user can reverse in a word, taken because the
benefit is permanent and the cost is bounded by this parking. **Two expected
reds, and that is the whole set.** Before reading either as new, **check the
pinned release rather than the board's branch**: the branch carries the repair
and the pin does not.

**What would end it: a new `s905x5m` release and a pin move in `mica-build`.**
Both are named so that when they happen this paragraph is **visibly stale
rather than quietly wrong** — a parked-state note without an exit condition
becomes a permanent description of a temporary state. And it is written at all
because of the decay path: **an expected red that somebody is waiting on gets
treated as flaky, and then it gets muted** — waiting, familiar, flaky, muted —
**and the mute outlives the reason.**

**And the boot question is open, not closed.** Nobody has established that this
defect has anything to do with the user's board failing to boot: the device
boots the **old, known-good** forced line, and **no console capture exists**.
**The investigation is paused rather than closed, which is exactly when that
assumption hardens into a fact nobody remembers doubting** — and the doubt is
written **in this paragraph** rather than elsewhere on purpose: **separation
is what lets the association form, because a doubt on another page is not a
doubt, it is a footnote to a fact.**
